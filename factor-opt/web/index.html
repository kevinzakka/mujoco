⚠ Honest limits

This is already-tuned double-precision sparse LDLᵀ, so wins are small single-digit by nature — a real ~1.33×, not a rewrite. The stated ceiling was 1.3×–1.6×; we landed in it.

The real correctness contract is tolerance, not bit-exactness: the comparator passes when ‖x_opt−x_ref‖∞/‖x_ref‖∞ ≤ 1e-6 plus the residual band — not max_solve_diff == 0. We re-ran the solve under that real contract: hand-written NEON on the L⁻¹ gather-dot, and full scoped compiler reassociation (-fassociative-math, which did perturb the output to max_solve_diff ≈ 2.6e-16 while staying comparator-PASS). Both gave 0% speedup beyond noise.

The reason is mechanical, not a tolerance gate: the solve's two hot passes are memory-bound on indexed gather/scatter (vec2[ind1[i]] and x[colind[adr]] -= …), and arm64 has no hardware gather/scatter. Widening the arithmetic can't help when the critical path is DRAM/cache latency on scattered addresses. So the solve ceiling is memory latency — the kept ≈1.33× build keeps the solve scalar (bit-exact, max_solve_diff == 0) because the vectorized variants buy nothing.
